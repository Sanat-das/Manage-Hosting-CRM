**What you'll get:** An IP provisioning step that automatically pulls the next free IP from the existing IP Manager when a VPS or Dedicated service goes live (plus an admin button to pick a specific IP or release it manually), and a new read-only "Asset relationships" admin area that links products and assets to each other and powers two canned reports — "Server hosting tree" and "Product-hosted-on product" — so an admin can answer questions like "which VPS live on SERVER01?"

**Why this approach:** The IP Manager already exists with a polymorphic assign column (`ip_addresses.assigned_to_type`/`assigned_to_id`) and an audit ledger (`ip_allocation_history`) built for exactly this — so we consume it instead of building a new pool. The product-to-asset link is reporting-only (no impact on orders, clients, billing, suspend/terminate) because none of WHMCS / Blesta / HostBill nests services-as-assets natively, and you explicitly asked for it to be report tooling, not lifecycle logic.

**What it will NOT do:** Add a new "Require IP" toggle/column on products (the existing "Require a domain" toggle already covers the domain need); rebuild the IP pool; couple the relationships to orders/clients/billing/suspend/terminate; push the assigned IP into the control panel (cPanel/Virtualizor) — that's a separate provisioning-module concern.

**Effort:** Short
**Risk:** Low — reuses existing models, additive only, no lifecycle coupling
**Decisions to sanity-check:** (1) IP provisioning is triggered by `product.type IN {vps, dedicated}` via a single `Product::requiresIp()` helper, not a new toggle column. (2) No convenience FK on `hosting_accounts` — the assigned IP is read via the polymorphic `assigned_to_type='HostingAccount'` pair only.

## Scope
### Must have
- **IP provisioning consumes the existing IP Manager.** When a VPS or Dedicated product is activated/provisioned, the system pulls the next available `ip_addresses` row from the relevant subnet/datacenter scope, marks it assigned to the `HostingAccount` (polymorphic `assigned_to_type='HostingAccount'`, `assigned_to_id=$account->id`), and writes one `ip_allocation_history` audit row. If no IP is available in scope, the activation fails with a friendly typed error instead of silently dropping the assignment.
- **Manual override + release in admin.** The hosting-account admin screen shows the currently-leased IP (read via the polymorphic pair) with three actions: "Pull next available", "Choose specific IP" (lists available IPs scoped to the account's server group's subnets), and "Release". Every action writes an `ip_allocation_history` row.
- **Read-only `asset_relationships` reporting layer.** A polymorphic-on-both-ends link table lets an admin relate a product to another product, or a product to a server, or any other asset pair, with a `relationship_type` (`hosted_on`, `hosted_in`, `manages`, `contains`). A small admin CRUD lets the admin build these links. **Purely reporting** — no order-blocking, no cascade, no billing impact.
- **Two canned admin reports** built on the link table: (1) "Server hosting tree" — pick a Server, see every VPS product/service hosted on it; (2) "Product-hosted-on product" — pick a product (e.g. shared hosting), see every other product it's hosted on. Both read-only, both CSV-exportable.
- Tests for every new rule, service, and screen (PHPUnit). `Product::requiresIp()`, `IpAssignmentService`, and the `AssetRelationship` saveGuard are pure logic → TDD. The Laravel-plumbing pieces (admin screens, integration into activation) → tests-after.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- NO new `require_ip` column / toggle on `products`. The "Require a domain" half of the original ask already exists end-to-end (Product model fillable `require_domain` + cast + `ProductRequest` rule + `ProductController::productData` wiring + create/edit/show blades) — leave it untouched.
- NO changes to `require_domain` semantics, `Product::TYPES`, `ProductResource` (that's the quota-entitlement layer, unrelated), or the existing `Server`/`ServerGroup`/`ServerGroupMember` models.
- NO new IP pool table, NO replacement of `ip_addresses`/`ip_subnets`/`ip_allocation_history` — consume them AS-IS.
- NO order-blocking validation, NO state cascade, NO suspend/terminate coupling for `asset_relationships` rows — they are reporting-only by explicit user decision.
- NO pushing the assigned IP into the actual control panel (cPanel/Virtualizor/DirectAdmin) — the lease lives in our DB only; panel-side assignment is a separate provisioning-module task.
- NO marketing cross-sell / "recommended products" tab (considered and explicitly declined).
- NO refactor of the IPAM admin CRUD that already exists under `admin.ip-addresses.*` — only ADD new behavior that calls into it.
