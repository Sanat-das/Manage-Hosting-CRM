# Gap Fill-Up — Feature & Logic Completion (Structure Only)

## TL;DR (For humans)

**What you'll get:** The four biggest feature/logic holes found when comparing this Laravel app against the v5 reference + web best-practice research, filled in priority order:

1. **Commerce flow** — the admin cart currently dead-ends (you can add items but never place the order). This adds the order-placement step, a proper order lifecycle (pending → paid → provisioning → active), race-safe order numbers, and the client-facing storefront so customers can order online.
2. **Real domain pricing & registrar integration** — domain availability search currently fakes results with hardcoded prices. This wires it to a real registrar driver (ResellerClub first, per the stored API credentials) with an RDAP pre-check and a `domain_pricing` table the admin can edit and sync.
3. **In-app notifications** — today the system only emails; several "notify when X happens" settings exist but do nothing. This adds an in-app notifications inbox (database-backed, Laravel-native), wires the dead toggles, and surfaces an unread-count badge in the client portal.
4. **Typed settings + missing data tables** — the settings page stores ~28 keys as free-text with no validation; the reference has ~170 keys in 17 groups. This adopts a typed settings layer and ports the missing groups (Domain, Integration, Hosting, IPAM, Catalog, Product, etc.) plus small ported tables (`tax_rates`, `marketing_consent_log`, `invoice_pdf_log`) and product bundles.

**Why this approach:** The gaps were verified against the reference (`.omo/plans/hosting-crm-adminlte.md` "reference as specification", v5 baseline) and the fill-up approach follows research on how WHMCS/Blesta/Paymenter do it: a cart is a transient basket, the order is the durable record with an explicit state machine, registrars are pluggable drivers behind a manager (exactly like the existing `PaymentGatewayManager`), notifications use Laravel's native database channel, and settings should be typed + validated rather than free-text rows.

**What it will NOT do:** **Zero theme/styling changes** — no AdminLTE skin edits, no CSS, no layout redesign. No changes to existing billing/suspension flows, no control-panel (cPanel/Plesk/DirectAdmin) push, no affiliate program, no webhooks module (both confirmed out of scope).

**Effort:** Large (4 tiers, executed one tier at a time, each independently shippable).
**Risk:** Low-Medium — everything is additive (new tables, new services, new routes); the only touched existing code is `DomainService::searchAvailability()` (stub replaced with real driver calls) and wiring already-dead settings toggles.

Your next move: approve the tier order (or reorder), then run `/start-work` to execute Tier 1.

## Scope

### Must have (by tier)

**Tier 1 — Commerce flow (highest priority: unblocks online ordering)**
- **T1.1** Order placement: `POST admin/cart/place-order` converting the session cart into an `Order` + `OrderItem`s, clearing the cart, redirecting to the order. Reuses the existing `Order` model (which already has `order_no` accessor, statuses, items, invoices relations).
- **T1.2** Order lifecycle state machine in a new `OrderService` (`app/Services/OrderService.php`): `pending → paid → provisioning → active` + `suspended`/`cancelled`/`terminated`, guarded transitions mirroring `DomainService`'s transition idiom. Research basis (Paymenter/WHMCS/Blesta): order = durable record, cart = transient; payment flips pending→paid, provisioning flips paid→active.
- **T1.3** Race-safe order/invoice numbering: extract `generateOrderNumber()` (currently duplicated in admin OrderController) into a shared `app/Services/OrderNumberService.php` using a `DB::transaction` + `lockForUpdate` on a sequence row, format `ORD-{YEAR}-{seq padded to 5}`. Applied to both admin cart and client store.
- **T1.4** Execute the existing client-storefront plan (`.omo/plans/client-store.md`) verbatim — `StoreController` (index/show/addToCart/updateCart/removeFromCart/cart/checkout/placeOrder/confirmation), 5 store views, `routes/client.php` store routes, sidebar entry, dashboard featured products. This is a pre-written, reviewed plan; execute it as written.

**Tier 2 — Real domain pricing & registrar integration**
- **T2.1** `App\Contracts\RegistrarDriver` interface (mirror `App\Contracts\PaymentGatewayDriver`): `checkAvailability(string $domain): array`, `register()`, `renew()`, `transfer()`, `isConfigured(): bool`, `isOnline(): bool`.
- **T2.2** `App\Services\Registrars\RegistrarManager` (mirror `PaymentGatewayManager` exactly: registry + `driverFor()` container resolution + `findByCode()`), singleton-registered in a new `RegistrarServiceProvider`. `RegistrarSetting` model already exists (`app/Models/RegistrarSetting.php` — imported by DomainService).
- **T2.3** `ResellerClubDriver` reading credentials from settings (resellerclub_api_id/api_key/username), calling the ResellerClub HTTP API. Research: standard registrar REST shapes; unconfigured driver must return `isConfigured() = false` and the availability path must degrade gracefully (typed error, never fake data).
- **T2.4** Rewrite `DomainService::searchAvailability()`: RDAP pre-check for availability (research: RDAP beats WHOIS for parse-ability), fall back to registrar driver for price; replace hardcoded `DEFAULT_TLD_PRICES` with `domain_pricing` table lookups; keep `domain_search_logs` recording. MUST NOT return fabricated availability/price.
- **T2.5** Port `domain_pricing` (+ `domain_pricing_terms`) + `domain_sync_log` tables via migrations; `DomainPricing` model; admin CRUD page (`admin.domain-pricing.*`) so the admin edits per-TLD pricing; a `domains:sync-pricing` scheduled command (added to the existing 6 scheduled commands) pulling prices from the configured registrar into `domain_pricing`.

**Tier 3 — In-app notifications**
- **T3.1** `notifications` table migration (Laravel's native `notifications` schema: `id uuid`, `type`, `notifiable` morph, `data json`, `read_at`, timestamps) + `NotificationPreference` table (morph `preferrable` + `channel` + `enabled`) mirroring reference `UserNotificationPreferences`.
- **T3.2** Wire the dead toggles: a `NotificationPreferenceService` mapping the existing settings keys (`notify_overdue_invoices`, `notify_domain_expiry`, `notify_new_tickets`, …) to preference rows; the 4 existing Events gain Listeners that dispatch DB notifications **and** respect preferences.
- **T3.3** New Events/Listeners (research: Laravel-native DB channel, `markAsRead`, prefs): `OrderPaid` → notify admin + customer; `InvoiceOverdue` → notify customer; `DomainExpiringSoon` (use existing `Domain::isExpiringSoon()`, tie into the existing `DomainExpiryCheckCommand`) → notify customer; `TicketCreated`/`TicketReply` → notify the counterparty. All respect `NotificationPreference`.
- **T3.4** Client portal: notifications list + "mark all read" + unread-count badge in the client sidebar (parity with reference `PortalService::getUnreadNotifications()`). Admin: a simple notifications dropdown/page. Real-time via polling is fine (research: Reverb optional, defer).

**Tier 4 — Typed settings + ported tables + bundles**
- **T4.1** Typed settings layer: adopt a settings package (research: **spatie/laravel-settings** recommended — typed classes, per-class caching, validation; alternative tobytwigger for schema-driven UI). Migrate the existing `settings` table reads: `SettingsController` gains per-group typed save with validation instead of the blanket `nullable|string|max:1000`; `AppSettings` stays as a thin cache wrapper or is replaced by the package's typed accessors. Keep existing keys working (no key renames).
- **T4.2** Port missing settings groups to typed settings classes + admin form tabs: Domain, Integration (cPanel/Plesk/ResellerClub creds), Hosting, IPAM, Inventory, Catalog, Product, Analytics, Automation, Cron, Role, User, Support — key sets from reference `modules/settings/presentation/cells/*/SETTINGS_KEYS`.
- **T4.3** Port small tables: `tax_rates` (+ wire into invoice line GST math — read-only reference first, GST columns already exist on `products`), `invoice_pdf_log` (record PDF generation), `marketing_consent_log` (consent opt-in/opt-out on client profile). Models + minimal admin pages where the reference has them.
- **T4.4** Product bundles: port `product_bundles` + `product_upgrade_paths` tables + models + admin CRUD. Bundle pricing = sum-of-parts + discount (research: WHMCS/Blesta model), cart expands bundle into components; `Product::TYPES['bundle']` becomes real. `product_upgrade_paths` only enforces valid upgrade paths (no billing engine changes).

### Must NOT have (guardrails, anti-slop, scope boundaries)
- **NO theme/styling changes of any kind** — no CSS, no AdminLTE skin edits, no layout/design changes, no new design tokens. Views added in this plan reuse the existing AdminLTE blade conventions exactly as the surrounding pages do.
- NO changes to existing billing/invoice/suspension/termination flows. `OrderService` only ADDS a state machine on top of existing statuses; existing transitions keep working.
- NO control-panel (cPanel/Plesk/DirectAdmin/Virtualizor) integration — `provisioning_module` columns stay as-is; provisioning adapters are explicitly out of scope.
- NO affiliate program, NO webhooks module, NO Reverb/WebSockets upgrade (polling acceptable).
- NO removing or renaming existing `settings` keys — additive only (new groups/keys).
- NO removal of `Domain::searchAvailability()`'s public contract — the method signature and return shape stay; only the internals become real.
- NO changes to `product_pricing`/`ProductPricing` semantics, `PaymentGateway*` classes, or the IPAM (`product-config-options.md` delivered) — consume as-is.
- NO fake availability/price data anywhere — an unconfigured registrar yields a typed error, never a fabricated "available".
