Deviations: none — every plan-named column and route exists under that name. Two documented implementation
choices, both inside the provider's own file:

- `HostingAccountSearchProvider::rankColumn()` returns `host_name`. The base class defaults ranking to the
  first searchable column (`username`), but the model's own docblock names `host_name` as "the product's
  identifier across the application", and the shared contract says the strongest identifier decides
  closeness — so the result label and the ranking column are the same identifier. Matching still covers all
  three columns.
- No eager loads are declared: none of the five `toResult()` methods touch a relation (labels/subtitles come
  from plain columns only), so adding `with()` would spend queries for nothing. The subtitle never contains
  a secret: hosting accounts use `domain ?: username` (never the legacy panel password), servers use
  `ip_address · server_type` (never `api_key`/`api_password_encrypted`), SSL uses `provider ?: certificate_type`.

All five list routes accept the `search` query param the foundation's "View all" links use
(`HostingController.php:104`, `ServerController.php:27`, `DomainController.php:28`, `SslController.php:38`,
`ServiceInstanceController.php:29` all `trim((string) $request->query('search'))`).

## Adversarial probes

### 1. Permission leak (the critical one)

Approach: the REAL seeded role grants, not hand-built permission sets. `TestCase::setUp()` runs
`AdminLteRbacSeeder`, so `panelUser('staff')` resolves exactly the matrix at
`database/seeders/AdminLteRbacSeeder.php:251-269` — and that matrix deliberately excludes `hosting.view`
(its comment explains it gates stored server credentials) and `service-instances.view`. `support` holds
`hosting.view` (`:194-213`).

Live observables:
- The test asserts the precondition from the same resolver the service uses:
  `assertContains('domains.view', $permissions)`, `assertNotContains('hosting.view', $permissions)`,
  `assertNotContains('service-instances.view', $permissions)` — so the denial is not a typo'd role name
  silently resolving to zero permissions.
- Staff groups for `acme`: `domains` present; `hosting`, `servers`, `ssl`, `service-instances` asserted
  ABSENT with dedicated failure messages ("Servers leaked to a viewer without hosting.view", etc.).
- Isolated run of the critical test:

### 2. Malformed input (literal `%`)

`test_a_literal_percent_in_a_hosting_identifier_is_matched_as_a_literal_not_a_wildcard`: two hosting
accounts, `host-50%` (literal percent) and `host-501` (ordinary). Querying the single character `%` returns
EXACTLY one result — `host-50%`, at `route('admin.hosting.show', $literal)` — so the term never degenerates
into a full-table dump. The generated SQL is asserted, not assumed: the captured `hosting_accounts` query
contains `ESCAPE '!'` and the binding `%!%%`.

### 3. Misleading success output (exact URLs + presence/absence)

- URLs are asserted with `assertSame(route('admin.servers.show', $server), ...['url'])` and
  `assertSame(route('admin.service-instances.show', $instance), ...['url'])` — equality with the
  server-resolved route, not `assertStringContainsString('/admin/')`.
- Group presence/absence is asserted with `assertContains`/`assertNotContains` on the actual group keys
  returned by `groups()`.
- The server lookup uses the provider's identifier (`ip_address`, not the name), the service-instance lookup
  uses `service_tag`; both fixtures are the only matching row, and `assertCount(1, ...)` guards against a
  stray row making the assertion accidentally pass.
